# 健康助手：面向日常问诊的多 Agent 可信健康建议平台

> 赛道一 · 健康助手 · 方案书
> 版本：v1.1（演示版）　日期：2026-11

---

## 一、项目背景与问题

### 1.1 用户真正需要什么

普通人身体不舒服时，第一反应往往是打开搜索引擎或通用大模型：输入"发烧喉咙痛怕冷"，得到一段看似专业、实则无法核验的回答。现有通用助手有三个突出问题：

1. **来源不可核验**：给结论不给依据，用户无法判断某条建议来自指南、说明书，还是模型编造；
2. **安全边界缺失**：不区分红旗症状，不提示禁忌人群，不检查正在服用的药物，甚至给出超剂量建议；
3. **过程不可解释**：一个黑盒一次性输出，用户不知道它"想过什么、查过什么、谁来把关"。

中医药场景更复杂：既要给常见、便宜、可及的中成药与药材，又要避免"寒热虚实"辨证错误，还要处理孕期、过敏、慢病与西药的相互作用。一个通用模型很难同时兼顾"便宜可及"和"安全边界"。

### 1.2 我们的判断

健康建议的可信度不来自"更大的模型"，而来自**分工、检索、审查与可追溯**。因此我们不做"一个更会说话的模型"，而是做一支**有明确角色、有工具、有审查、有轨迹的 Agent 团队**：

> 分诊 Agent → 辨证 Agent → 中药知识库 Agent → 并行检索 Agent（PubMed / openFDA / NHS-WHO-CDC）→ 撰写 Agent → 安全审查 Agent → 修复/降级。

每个环节的输入输出都进入轨迹，用户可以看到"谁在什么时候做了什么、依据是什么、审查发现了什么"。当某一步失败时，系统不是整体崩溃，而是降级：检索超时就标注"这次没取到内容"，模型不可用就切 Mock，审查不通过就修复或降级为模板安全回答。

### 1.3 目标场景与典型用户

- **上班族**：发烧咽痛，想知道能不能先吃点中成药、要不要请假就医；
- **年轻女性**：痛经、失眠，希望得到便宜可及的中成药与生活调整建议；
- **孕妈妈**：感冒了不敢乱吃药，需要孕期禁忌过滤；
- **慢病老人**：同时吃丹参片和感冒药，担心相互作用；
- **情绪困扰者**：压力大、睡不着，需要可执行的建议与求助路径；
- **普通家庭**：想知道冰箱里的食物是否健康、怎么搭配。

这些场景的共同点是：**风险不高但决策频繁、信息不对称、用户需要"能看懂的依据"**。这正是多 Agent 流水线比单次生成更合适的地方。

---


### 1.4 与现有方案的区别

| 方案 | 优点 | 不足 |
|---|---|---|
| 搜索引擎 | 信息多、来源杂 | 需要用户自己筛选，广告与谣言混杂 |
| 通用大模型 | 回答流畅、即时 | 来源不可核验、安全边界弱、过程黑盒 |
| 线上问诊 | 有医生参与 | 贵、慢、轻症不划算 |
| 本平台 | 来源可查、审查可看、轨迹可复盘、便宜可及 | 知识库待专业审核、样本仍小 |

我们不是替代医生，而是把"轻症决策"这一段做得更可信：先排除红旗，再给可核验的选项，最后用审查兜底。


### 1.5 设计原则

- **先安全，后有效**：红旗识别永远优先于药物推荐；
- **先可核验，后流畅**：宁可回答短一点，也要每条引用有出处；
- **先可解释，后智能**：用户能看见每一步，才谈得上信任；
- **先可降级，后完美**：任何外部依赖失败，系统都要有兜底路径；
- **先可复现，后宣传**：所有指标都能在仓库里重跑，不靠口头承诺。

## 二、总体方案

### 2.1 产品形态

- 单页 Web 应用，本地一键启动（`http://127.0.0.1:8100`），开箱即用、不需要登录；
- 中文对话式交互，回答中不夹杂英文原文；
- 默认使用本地 Mock 模型，**零 token、断网也能演示**；配置 DeepSeek Key 后可切换真实模型；
- 所有个人数据（画像、用药、计划、记忆）存本机 SQLite，不上传云端；
- 左侧栏集中所有功能：对话、我的药、团队与流程、对比实验、消融实验、个人资料、康复计划。

### 2.2 多 Agent 流水线

| 阶段 | Agent/模块 | 职责 | 产出 |
|---|---|---|---|
| 1 | 路由 Agent | 判断问诊/心理/食物/闲聊，混合意图先澄清 | 意图 + 置信度 + 理由 |
| 2 | 分诊 Agent | 红旗症状识别、紧急度分级 | 是否需立即就医 |
| 3 | 辨证 Agent | 寒热虚实、需要追问的关键问题 | 证型/待确认项 |
| 4 | 知识库 Agent | 中成药/药材/西药/食物/心理主题匹配 | 候选清单 + 用法禁忌 |
| 5 | 并行检索 Agent | PubMed、openFDA、NHS/WHO/CDC 三路并发取证 | 证据条目 + 来源 |
| 6 | 撰写 Agent | 汇总为结构化报告（首选药、用法、禁忌、膳食、运动） | Markdown 报告 |
| 7 | 安全审查 Agent | 引用锚定、剂量出处、免责声明、红旗提示、相互作用 | 问题清单 |
| 8 | 修复/降级 | 有问题则修复，仍不合格降级为模板安全回答 | 最终回答 + 审查记录 |

每个阶段的设计细节：

- **路由**：先用关键词规则打分，低置信度时再让模型判断；当两个意图分数接近（如"心情不好，失眠"），不硬猜，返回澄清卡片让用户点选；
- **分诊**：内置红旗词表与模式（胸痛、呼吸困难、意识改变、持续高热等），命中即进入紧急路径，只给就医建议，不推荐药物；
- **辨证**：根据症状判断风寒/风热/寒湿等，信息不足时生成追问（怕冷还是怕热、痰的颜色、是否出汗），用户可跳过直接生成；
- **知识库**：按证型、症状、人群禁忌检索，返回 4–5 个选项（中成药 + 药材 + 备用西药），并附价格区间与 OTC 标识；
- **并行检索**：三路 HTTP 并发，单路超时不影响其他路；每条证据记录来源、标题、摘要、链接；
- **撰写**：把证据、知识库、画像、用药合并成结构化报告，正文中的每个引用都必须来自证据清单；
- **审查**：检查引用是否可在清单中定位、剂量是否有出处、是否含免责声明、红旗场景是否给了就医提示、是否存在药物相互作用；
- **修复**：审查发现问题时尝试补引用/改表述；仍不通过则降级为"安全模板"，明确告知用户信息不足。

### 2.3 知识库

| 库 | 规模 | 内容 |
|---|---|---|
| 中成药 | 60 条 | 名称、证型、功效、用法、禁忌、注意、价格区间、OTC/处方 |
| 中药材 | 78 条 | 性味归经、功效、常用剂量、禁忌、配伍提示 |
| 西药 | 28 条 | 适应证、用法、禁忌、不良反应、孕妇/儿童提示 |
| 食物 | 158 条 | 热量、三大营养素、膳食纤维、钠、健康标签、益处/风险 |
| 心理主题 | 25 个 | 压力、焦虑、低落、失眠、校园霸凌等，含应对建议与求助路径 |
| 危机资源 | 多条 | 12356、400-161-9995、北京/上海/广州热线与就医提示 |

数据来源标注为中国药典/说明书、USDA FoodData Central、中国食物成分表（第 6 版）、WHO、NHS 等；当前为**演示数据集**，上线前需药师/营养师/心理师抽样复核。知识库以 JSON 存储，带校验脚本，字段缺失或剂量格式异常会在启动时被检查出来。


### 2.3.1 知识库的校验与更新

- 启动时运行 `scripts/validate_kb.py`：检查必填字段、剂量格式、价格区间、禁忌字段是否为空；
- 每条药物带 `source` 字段标注来源（药典/说明书/机构），缺来源的条目在报告里会提示"来源待补充"；
- 更新流程：新增条目 → 校验脚本 → 抽样人工复核 → 版本号 +1；
- 演示版把版本号写在 README 与 `/api/meta`，方便评委确认当前用的是哪一版。

### 2.4 个性化与安全

- **用户画像**：年龄、性别、孕期、过敏史、慢病；每次分析自动带入；
- **相互作用**：内置常见组合规则（如布洛芬 + 活血中药、对乙酰氨基酚 + 酒精），并对西药组合查询 openFDA 说明书原文，命中则引用；查不到时明确提示"未覆盖，请咨询药师"；
- **跨会话记忆**：从对话中抽取过敏/慢病/孕期，写入画像；支持修改、删除、清空历史记录；带否定句识别（"我没有青霉素过敏"不会写入）；
- **用药安全**：孕期禁用活血类中药、过敏药物过滤、复方感冒药重复成分提示；
- **危机识别**：高/中/低风险分级，高危直接给热线与就医建议，24 小时后回访。

### 2.5 长期管理

- **我的药**：提醒（间隔/每天次数/首次时间）+ 疗程龙珠打卡 + 库存 + 有效期，四件事一条记录；
- **一周康复计划**：自动从建议生成，每日打卡 + 症状评分（0–10）+ 趋势曲线；第 7 天按评分自适应：好转自动延长一周，无改善提示复诊；
- **提醒通道**：页面内通知、队列化后台扫描、Windows 通知器（登录常驻）、Web Push（跨设备，受推送服务可达性限制）。

## 三、多 Agent 的价值：可量化证据

### 3.1 单 Agent vs 多 Agent（DeepSeek，4 例）

| 指标 | 单 Agent | 多 Agent |
|---|---|---|
| 平均耗时 | 5.33 s | 49.48 s |
| 平均 token | 676 | 10,745 |
| 引用可核验率 | 0% | **100%（3/4 例有来源）** |
| 平均安全审查问题数 | 4.25 | **0** |
| 含免责声明 | 0/4 | **4/4** |
| 红旗场景正确率 | 4/4 | 4/4 |

代价是更慢、更贵；收益是**每条结论都有来源、每个回答都过审查**。对健康场景，这个交换是值得的，且可通过缓存与 Mock 降低演示成本。胸痛用例中多 Agent 耗时显示 0 秒，是因为走了紧急路径直接给出就医建议，没有继续检索与推荐药物——这是安全设计，不是失败。

### 3.2 消融实验（Mock，6 例）

| 变体 | 平均耗时 | 可选药物 | 来源数 |
|---|---|---|---|
| 完整流程 | 1.59 s | 7.0 | 16.5 |
| 去掉安全审查 | 1.53 s | 7.0 | 16.5 |
| 去掉知识库 | 2.95 s | **0.0** | 9.2 |
| 去掉并行检索 | **3.99 s** | 7.0 | 16.5 |

- 去掉知识库：药物候选直接归零，说明"检索 + 知识库"不是装饰；
- 去掉并行：耗时约翻倍，证明并行取证的价值；
- 审查在模板路径上不产生问题，但**注入错误**后能抓住"布洛芬一次 800 mg、每天 4 次"这类无依据剂量。

### 3.3 路由与安全

- 混合意图（"心情不好，失眠"）→ 反问澄清；点选后强制进入对应流程；
- 路由 Agent 在 12 条标注用例上 **12/12**，全部当问诊的基线为 25%；
- 注入测试：干净报告 0 问题，注入 2 条无依据剂量/疗效表述后审查抓到 1 条；
- 红旗用例（胸痛、呼吸困难）走紧急路径，不推荐药物。

### 3.4 评测方法与局限

- 对照实验选 4 个典型用例（发热咽痛、高热头痛、胸痛呼吸困难、咳嗽黄痰），覆盖轻症与红旗；
- 指标包括耗时、token、引用可核验率（正文引用能否在来源清单中定位）、审查问题数、免责声明、红旗正确率；
- 消融实验用 Mock 固定输出，比较流程变体的耗时、药物数、来源数，避免模型随机性；
- 局限：样本小、无临床金标准、审查问题数由本平台规则计算，不代表独立临床评审；结论应理解为"工程有效性"而非"临床有效性"。

### 3.5 工程可信度

- 68 个自动化测试（单元 + API + HTTP 级 E2E），覆盖安全、记忆、计划、用药、缓存、重置；
- 前端拆分为 `index.html` / `styles.css` / `app.js`，有静态资源断言；
- 响应缓存（10 分钟）让重复提问从 1–2 秒降到 0 ms；SQLite 开启 WAL 提升并发读写；
- 断网兜底：`DEMO_OFFLINE=1` 用证据缓存，Mock 模型不产生外网请求。


### 3.6 失败模式与降级策略

| 失败场景 | 系统行为 | 用户看到 |
|---|---|---|
| PubMed/openFDA 超时 | 单路失败不阻塞，其余证据继续 | 轨迹标"这次没取到内容" |
| 三路全失败 | 用知识库 + 模板撰写 | 明确"检索不可用，建议仅供参考" |
| DeepSeek 不可用 | 自动降级 Mock | 模型标识变为 mock |
| 审查发现问题 | 先修复，再审查一次 | 修复记录进入轨迹 |
| 修复后仍不合格 | 降级为安全模板 | 只给通用建议 + 就医提示 |
| 红旗症状 | 跳过药物推荐 | 直接就医建议 + 急救提示 |
| 图片模型未加载 | 首次加载，超时兜底 MobileNetV2 | 稍慢但可用 |

这张表是我们对"可靠性"的理解：不是保证永远不出错，而是出错时**有明确的降级路径**，并且用户能看见。

## 四、创新点

1. **"团队"而非"单体"**：角色、工具、审查分离，轨迹可解释；不是把提示词写长，而是让每个 Agent 只做一件事并留下证据。
2. **引用锚定审查**：把"有没有来源"变成可执行的审查规则，模型写错引用会被抓出来；这是与通用助手最本质的差异。
3. **中西医结合的安全层**：中药辨证 + 西药说明书 + 相互作用 + 孕期/过敏/慢病过滤，覆盖常见家庭用药场景。
4. **记忆可纠正**：自动抽取 + 否定句识别 + 手动修改/删除 + 清空，避免"越记越错"；这是长期使用的前提。
5. **闭环到行为**：从"给建议"到"提醒吃药、疗程打卡、一周康复、趋势判断"，把一次性问答变成可执行计划。
6. **可复现的评测**：对照实验、消融实验、注入测试、路由标注集，全部在仓库内可重跑，评委可以自己验证。

## 五、演示流程（3 分钟）

1. **问诊**（20–60 s）：输入"发烧，咽喉痛，有点怕冷，两天了"，展示分诊红旗判断、辨证追问、中成药 + 药材 + 备用西药、来源清单、安全审查结果；
2. **轨迹**（60–80 s）：打开"轨迹"，展示 8 个 Agent 的分工、并行检索的三路证据、审查步骤；
3. **对比与消融**（80–110 s）：展示单 Agent vs 多 Agent 的引用可核验率与审查问题数；展示"去掉知识库药物归零、去掉并行耗时翻倍"；
4. **心理支持**（110–140 s）：输入"最近压力大，睡不着"，展示心理主题建议与求助资源；补充说明危机识别会直接给热线；
5. **食物识别**（140–165 s）：上传一张坚果/炸鸡图片，展示健康/垃圾食品判断、营养与利弊；
6. **我的药 + 康复计划**（165–180 s）：打卡一次点亮龙珠、查看库存；打开康复计划看趋势曲线与第 7 天自适应规则。

断网时全流程用 Mock + 本地知识库，仍可完成 1、2、4、5、6。

## 六、边界、风险与合规

### 6.1 明确不做什么

- 不提供诊断，不开处方，不替代医生；
- 不覆盖急危重症的院前处置（只做识别与就医建议）；
- 不做药物剂量个体化调整（按说明书常用量，特殊人群提示咨询医生）；
- 不保证知识库覆盖全部药物与相互作用。

### 6.2 数据与来源声明

- 知识库为**演示数据集**，来源标注为药典/说明书/权威机构，但尚未经过执业药师逐条审核；
- 价格、库存、有效期均为演示值；
- 引用来自公开网页/说明书摘要，可能随时间变化；
- 平台输出仅供健康科普参考，出现不适请就医。

### 6.3 安全边界

- 红旗症状优先就医，不推荐药物；
- 孕期、过敏、慢病、正在用药会改变推荐与提示；
- 相互作用"查不到"不等于"没有"，提示咨询药师；
- 危机场景给热线与就医建议，不进行心理治疗。

### 6.4 隐私

- 数据存本机 SQLite；默认 Mock 不外发；
- 选择 DeepSeek 时仅发送当前症状文本，不上传历史对话与用药记录；
- 演示版为单用户本地模式，未做账号隔离与传输加密；公网部署需加 TLS、鉴权与数据加密。


### 6.5 伦理与责任

- 平台定位是健康科普与决策辅助，不建立医患关系；
- 所有回答附带免责声明，红旗场景强制就医提示；
- 不收集身份证、病历号等敏感身份信息；症状文本仅用于当次分析；
- 危机场景优先连接社会支持资源，不进行替代性心理治疗；
- 若未来上线，需要明确责任主体、投诉渠道与不良事件上报机制。

## 七、工程实现

- 后端：FastAPI + SQLite（WAL），模块化（pipeline / triage / syndrome / kb / evidence / report / safety / memory / meds / plan / notify / push / food / psych / router）；
- 前端：原生 JS 单页，三文件拆分，轨迹抽屉、对比实验、消融实验、药品柜、康复计划、个人资料；
- 模型：DeepSeek OpenAI 兼容接口，失败自动降级 Mock；Mock 结果确定、可离线；
- 检索：PubMed E-utilities、openFDA、NHS/WHO/CDC 网页抓取，超时降级并记录；
- 图片：CLIP zero-shot（RN50）+ MobileNetV2 兜底，首次使用时加载，CPU 可跑；
- 测试：`uv run pytest -q`，68 项；E2E 在运行中的服务上验证完整用户流程；
- 部署：systemd 服务 `health-panel.service`，重启即生效；
- 性能：响应缓存 10 分钟、SQLite WAL、并行检索、按需加载模型。

### 7.3 一次请求的数据流

1. 前端把症状、画像、用药、历史记忆一起提交；
2. 路由 Agent 判定意图；问诊进入分诊，心理进入主题匹配，食物进入检索；
3. 分诊命中红旗 → 直接返回就医建议；否则辨证并生成追问；
4. 知识库按证型/症状召回候选，并行检索补充外部证据；
5. 撰写 Agent 生成报告，引用只允许来自证据清单；
6. 审查 Agent 检查引用、剂量、免责声明、相互作用；
7. 结果写入对话历史与记忆，前端渲染报告与轨迹；
8. 相同问题再次提问时命中响应缓存，直接返回并标注"缓存"。

## 八、局限与后续工作

1. 知识库需专业审核与版本化，当前是演示数据集；
2. 评测样本仍偏小（对照 4 例、消融 6 例、路由 12 例），需要更大规模与临床金标准；
3. 多 Agent 成本高（约 1 万 token/次），需要缓存、蒸馏与按需检索；
4. 记忆抽取仍基于规则，复杂否定/第三人称可能误判；
5. 提醒跨设备依赖推送服务可达性；
6. 未做账号体系与端到端加密（演示版有意简化）；
7. 危机回访目前只做 24 小时提醒，未接入人工干预；
8. 食物识别只做单食物，复杂菜品与分量估计仍有限。


### 8.1 里程碑

- 第 1 阶段（已完成）：多 Agent 主流程、知识库、安全审查、轨迹、对照/消融实验；

- 第 3 阶段：接入正规药品/相互作用数据库，支持多用户与数据加密；

后续计划：

- 长期：与社区医院/药房合作做真实场景验证。

## 九、结论

我们做的不是"一个会聊天的健康机器人"，而是一支**能查、能审、能解释、能落地到行为**的 Agent 团队：每个结论有来源，每个回答过审查，每一步可复盘。评测显示，多 Agent 在引用可核验率（0% → 100%）与安全审查问题数（4.25 → 0）上有明确收益；消融实验证明知识库与并行检索各自不可替代。平台已可本地一键运行、断网演示，并保留了继续扩展的清晰边界。

对比赛而言，它的价值不在于"功能多"，而在于**把健康建议的可信度做成了可以被检验的东西**：来源可查、审查可看、消融可复现。这也是我们理解的"健康助手"应有的样子。
